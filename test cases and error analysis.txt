ALL DOCUMENTED AGENT TESTING ERROR CASES AND EXPLANATION

Analysis of failed test requests from the agent testing log, root causes, and corrections applied
1. Summary
The testing log recorded 22 requests against an LLM-driven agent (backed by employee/project/task/project_updatesdata) across three models: llama3.2 (local), qwen3:4b / qwen3.2:4b (local), and Gemini-3.5-flash-lite. Out of these four requests produced a failing result.

2. Detailed Error Cases
Error Case 1, Request 10: Multi-step tool call not completed (llama3.2)
Question: "how many project updates does project beta have? and how many of them are high risk" (model: llama3.2)
What went wrong: Instead of retrieving project updates and answering, the agent replied "Replan: Before fetching the project updates, let's first retrieve the project details using get_project. Please confirm if you would like to proceed?" so it stalled mid-plan and asked for confirmation that wasn't needed, instead of chaining the two required tool calls (get_project ->  get_project_updates) and returning the counts.
Why it happened (root cause): The request requires a two-part answer derived from at least two sequential tool calls plus a count/filter step (total updates, then how many are high-risk). llama3.2 is not reliably capable of this kind of multi-step tool orchestration, so it produced a partial plan, then paused and asked for unnecessary confirmation rather than continuing.
Fix /handling: The same request was re-sent unchanged to two stronger models. qwen3:4b correctly chained get_project -> get_projects ->  get_project_updates and returned the exact expected answer (3 updates, 0 high-risk). Gemini-3.5-flash-lite did the same. The fix applied was a model swap, not a prompt or code change. llama3.2 was identified as unreliable for multi-step tool chains and qwen3:4b/Gemini were used going forward for this type of requests.
Status after fix: Resolved by switching models, confirmed working on qwen3:4b and Gemini-3.5-flash-lite.




Error Case 2, Request 17: Remembered task not executed (llama3.2)
Trigger: "do the task I wanted you to remember today", following an earlier turn (Request 16) where the agent was told to remember "updating upd4 to risk level high" (model: llama3.2)
What went wrong: The agent replied "The task to update upd4 to risk level high has been remembered. I will keep this in mind..."  So it restated/re-stored the memory instead of retrieving it and calling the update tool (update the risk level of UPD4).
Why it happened (root cause): This tests a harder pattern rather than a simple plain recall: the agent must first  look up what was stored in memory, and then recognize that the stored content is an instruction to perform an action rather than a fact to report, and then  invoke the correct tool with the right arguments. llama3.2 could recall that something was stored, instead conflated 'retrieve context' with 'take action on that context' and treated it as a save operation again rather than an execution trigger. SO it failed badly
Fix/handling: The same request with same body was re run on qwen3.2:4b, which correctly retrieved the memory, understood it as an actionable instruction, and called the update tool resulting in UPD4's risk level being changed from low to high, matching the expected answer. Similar to error Case 1, the solution was using a model with stronger tool use/instruction following/reasoning ability for these kind of questions.
Status after fix: Resolved by switching models, confirmed working on qwen3.2:4b.


Error Case 3: Request 19: Memory lost after server restart
Trigger: "what did I ask you to remember today?" sent immediately after restarting the server (model: qwen3.2:4b, userId: suresh)
What went wrong: The agent replied "I do not have a saved preference for you yet" even though the same user's memory had been successfully stored and retrieved earlier in the session (Requests 16 to 18).
Why it happened (root cause): The agent's memory/context was being held only in an in-process cache. Restarting the server cleared that cache. Although the data had also been persisted to memory.json on disk, the running agent never re-read that file on startup, so from the agent's perspective the user had no history. This is a mismatch between what was stored and what the running process actually used .
Fix / handling: A user-scoped, persisted memory lookup path was added. The agent now checks memory.json (keyed per userId) before responding, instead of relying solely on the in-memory cache. This makes stored context survive server restarts.
Status after fix: Resolved. Re running the same request after implementing the fix (Request 20) returned the correct remembered task, confirming context now survives a server restart.


Error Case 4: Requests 21 & 22: Complex multi-part request exceeds tool-call budget / times out
Trigger: "Analyze all active projects, identify the highest-risk projects, find the employees responsible for their overdue tasks, check their latest updates, and recommend actions... calculate how many odd numbered tasks have todo status" (tested on llama3.2, qwen3:4b, and Gemini-3.5-flash-lite)
What went wrong: Request 21 (limit = 15 tool call iterations): the agent returned "I could not complete the request within the tool call limit" after using calls like create_plan, get_projects, get_project_metrics, find_project_risks, get_project_updates, get_tasks without reaching a final answer. Request 22 (limit raised to 30): llama3.2 ran for 40+ minutes with no answer and I had to stop it.  Gemini-3.5-flash-lite hit its 15 requests-per-minute rate limit and returned a 429 error. All three models failed to produce an answer for this request.
Why it happened (root cause): The request combines many independent sub-tasks (cross-project risk analysis, ownership lookup, overdue-task tracing, update review, recommendation generation, plus an unrelated numeric filter over tasks) into one message. Answering it correctly requires a long, sequence of tool calls. At a 15 call cap the agent simply ran out of iterations before finishing. Raising the cap to 30 didn't fix it. The search/reasoning space is large enough that local models (llama3.2, qwen3:4b) took excessive time without answering, and Gemini triggered its rate limit before the plan could complete.
Fix/ handling: This is not resolved by raising the iteration limit alone, that only pushed the failure mode from "limit reached" to "time out/ rate limited." SO I am documenting this case as an open limitation which cannot be solved by this current project. It needs request splitting (splitting the task into smaller sequential requests), a very capable model for this specific query, and higher rate limit aware models, rather than simply raising the iteration ceiling.
Status after fix: Unresolved, flagged as a limitation rather than a bug fixed


3. Conclusion
18 of 22 requests passed on first attempt, and all 4 failures were either resolved by a model swap or a persistence fix, except the multi part query which is not fixed, and which remains an open scaling problem.
