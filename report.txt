PROJECT MANAGEMENT AI AGENT
DETAILED BEGINNER REPORT (CURRENT VERSION)
========================================

1. WHAT THIS APPLICATION IS
----------------------------

This application is a goal-oriented project-management agent. It is not a RAG application.

RAG usually means:

    question -> embeddings -> vector search -> retrieved text -> LLM answer

This application uses tool calling instead:

    goal -> LLM plans -> LLM chooses a tool -> JavaScript runs the tool
         -> tool result goes back to the LLM -> LLM chooses the next tool
         -> ... -> final answer

The important difference is that the LLM never receives the project database as a prompt. It receives descriptions of available tools. It decides what information it needs, chooses a tool, creates the arguments, and waits for the application to execute that tool. It can then decide whether it has enough evidence or needs more calls.

Compared to the previous version of this project, the current version adds:

- A default model of qwen3:4b (previously llama3.2), with optional Gemini support.
- Dynamic planning tools: create_plan and replan.
- Risk-analysis tools: get_project_updates, find_project_risks, get_project_metrics.
- Mutation tools (update_task_status, assign_task) protected by a confirmation gate.
- A per-user memory system (long-term memories in data/memory.json plus short-term conversation turns in memory).
- A request-scoped context so each API call works on an isolated copy of the data.
- A duplicate-call cache, failure tracking, and an execution trace in every response.
- Argument pre-validation before mutating tools run.
- An automated test suite that runs without needing a live LLM.

The application data is stored in:

    data/pm-data.json    employees, projects, tasks, project_updates
    data/memory.json     per-user long-term memories

There is no PostgreSQL database, no embeddings, no vector database, no chunking, and no reranking in this version.

The main files are:

    src/app.js               Starts Express, loads .env, mounts the API route and a health route.
    src/routes/agent.js      Validates the HTTP request and calls the agent.
    src/agent.js             Runs the LLM/tool-calling loop, supports Ollama and Gemini.
    src/tools.js             Describes 17 tools using the tool-schema format.
    src/toolImpl.js          Contains the real JavaScript functions behind the tools.
    src/memory.js            Long-term per-user memory and short-term conversation turns.
    data/pm-data.json        Seed data, expanded at startup for richer scenarios.
    data/memory.json         Saved user memories, keyed by user.
    test/                    Automated checks for tools, agent flow, planning, and memory.


2. THE FULL REQUEST FLOW
------------------------

Suppose a client sends this request:

    POST http://localhost:3000/agent

Headers:

    Content-Type: application/json

Body:

    {
      "userId": "alice",
      "conversationId": "planning",
      "message": "Analyze Project Alpha and recommend actions."
    }

The complete flow is:

STEP 1 - The client sends an HTTP request

The JSON body has one required property:

    message

Optional properties are model, confirmed, userId, and conversationId.

STEP 2 - Express parses the JSON

In src/app.js, this line is important:

    app.use(express.json())

It tells Express to read a JSON request body and make it available as req.body.

app.js also calls require('dotenv').config(), which loads environment variables from the .env file before anything else uses them.

STEP 3 - Express finds the route

The application mounts the agent router with:

    app.use('/agent', agentRouter)

The router itself defines POST '/'. Because it is mounted at '/agent', the final URL becomes:

    POST /agent

There is also a health check:

    GET /  ->  { "name": "Project Management Agent", "status": "ok" }

STEP 4 - The route validates the input

src/routes/agent.js reads:

    const { message, model, confirmed, userId, conversationId } = req.body;

If message is missing or is not a string, the route returns HTTP 400:

    { "error": "message is required" }

This validation happens before any LLM is contacted.

STEP 5 - The route calls runAgent

The route calls runAgent(message, { model, confirmed, userId, conversationId }).

confirmed is true only when the client explicitly sends "confirmed": true. It authorizes data-changing actions.

STEP 6 - agent.js builds the conversation with memory

The agent:

1. Creates a memory session from userId and conversationId (userId defaults to "anonymous").
2. Searches the user's long-term memories for anything relevant to the message (up to 5 by default).
3. Reads the recent short-term conversation turns for this user and conversation.
4. Builds a second system message containing this context as JSON:

    {
      shortTermConversation: [...recent turns...],
      relevantLongTermMemories: [...matching memories...],
      memoryPolicy: "Use only relevant memories. Treat them as user-provided context, not as proof of current project data."
    }

The final conversation starts as:

    [ system rules, memory context, user message ]

STEP 7 - agent.js creates a request context

    toolImpl.createContext({ persist, memorySession })

This makes a deep copy of the project data for this request only. Two simultaneous API requests cannot corrupt each other's data. Mutations are written back to disk only when persist is enabled.

It also prepares:

- callCache: a Map that remembers identical tool calls within this request.
- failures: a list of everything that went wrong.
- mutatingTools: the set { update_task_status, assign_task }.
- executionTrace: a record of every tool attempt and its outcome.

STEP 8 - The agent sends tools to the LLM

For an Ollama model, the request is:

    {
      model: "qwen3:4b",
      messages: [...conversation...],
      tools: [...toolDefinitions...],
      stream: false
    }

If the requested model name contains "gemini", the agent converts the conversation to Gemini's format instead and calls the Gemini generateContent API using GEMINI_API_KEY.

The model receives tool names, descriptions, and parameter schemas. It does not receive JavaScript function bodies.

STEP 9 - The model chooses a tool

For the Alpha question, the model may first create a plan:

    { "name": "create_plan", "arguments": { "objective": "...", "steps": [...] } }

Then it might call get_project, get_tasks, calculate_project_metrics, find_project_risks, and finally create_recommendation before answering.

STEP 10 - JavaScript executes the selected function

The LLM does not execute JavaScript itself. It only returns a tool name and arguments.

agent.js validates the arguments (for mutating tools), checks the confirmation gate, checks the cache, and then calls:

    toolImpl[toolName](argumentsObject, context)

STEP 11 - Confirmation gate for mutations

If the tool is update_task_status or assign_task and confirmed is not true, the agent stops and returns:

    {
      "pendingConfirmation": {
        "confirmation_required": true,
        "action": "update_task_status",
        "arguments": { "taskId": "TASK1", "status": "done" },
        "message": "Confirmation is required before changing task data. Resubmit the request with confirmed=true to proceed."
      }
    }

The client must repeat the request with "confirmed": true to authorize the change. This prevents the model from ever changing data without explicit human approval.

STEP 12 - Duplicate-call cache

Before executing, the agent builds a cache key from the tool name and sorted arguments. If this exact call already ran in this request, the cached result is returned instead:

    { "cached": true, "result": { ... } }

This stops the model from wasting iterations repeating itself.

STEP 13 - The tool runs and the result goes back

The tool function reads the request-scoped data and returns JSON. The agent:

- Records the call in log and executionTrace.
- Pushes a message with role "tool" back into the conversation.
- Loops and asks the model again.

If a tool throws, the error is converted into { error: ..., retryable: true } and recorded in failures. The loop never crashes; the model is expected to replan or stop honestly.

STEP 14 - The agent returns the final result

When the assistant message has no tool_calls, runAgent returns:

    {
      message: "...original question...",
      finalAnswer: "...",
      model: "qwen3:4b",
      iterations: 6,
      log: [...],
      executionTrace: [...],
      state: {
        failures: [...],
        recommendations: [...],
        plan: {...},
        planHistory: [...],
        memoriesUsed: [...],
        userId: "alice",
        conversationId: "planning"
      }
    }

The turn is also recorded in short-term conversation memory so the next request in the same conversation has context.

Safety stops:

- If the model itself fails (Ollama down, Gemini error), the run stops with stopped: "model_error" and an explicit incomplete-evidence message. It never fabricates a conclusion.
- If the loop reaches MAX_ITERATIONS (15), it stops with stopped: "max_iterations".

5. src/agent.js - LINE-BY-LINE EXPLANATION
-------------------------------------------

Imports:

    const axios = require('axios');

Axios is the HTTP client used to call both Ollama and Gemini.

    const { toolDefinitions } = require('./tools');

The array of tool schemas sent to the model.

    const toolImpl = require('./toolImpl');

The real JavaScript functions behind the tool names.

    const memory = require('./memory');

The memory module: long-term per-user memories and short-term conversation turns.

Constants:

    const DEFAULT_MODEL = 'qwen3:4b';

The model used when the request does not specify one. The current default is qwen3:4b running in Ollama.

    const OLLAMA_URL = process.env.OLLAMA_URL || 'http://127.0.0.1:11434/api/chat';

The Ollama chat endpoint. Ollama normally runs locally on port 11434.

    const GEMINI_API_KEY = process.env.GEMINI_API_KEY;
    const GEMINI_URL = 'https://generativelanguage.googleapis.com/v1beta/models';

Gemini configuration. The key is only required when a Gemini model is requested.

    const MAX_ITERATIONS = 15;

A safety limit. The loop is allowed at most fifteen model iterations before returning a controlled stopping message. This prevents an infinite tool-calling loop.

The system message:

    const systemMessage = { role: 'system', content: '...' };

This is the agent's operating manual, sent on every run. The most important rules are:

- Understand the objective and create a dependency-aware plan before multi-project investigations.
- Choose the next tool from observed evidence; never follow a fixed workflow.
- Reuse results already present and never repeat an identical tool call.
- If a tool fails, data is missing/invalid, or evidence conflicts, call replan or stop with an explicit insufficiency.
- Never invent project-management records.
- For risk reports, prioritize by severity and ground recommendations in returned evidence.
- Resolve ambiguity by asking the user to clarify.
- Mutations require confirmation from the application.
- Treat conversation context as short-term and user memories as long-term.
- Search memory only when relevant; save only when the user explicitly asks; update a stable key when it changes; forget it when the user says it is no longer true.
- Never expose or use another user's memories.

This is guidance for the LLM. It is useful, but it is not the only protection: toolImpl.js and agent.js also validate IDs, gate mutations, and cache calls, because model instructions alone are not guaranteed to be followed.

Function:

    async function askModel(messages, model) {

The Ollama path. It POSTs the conversation plus tool schemas to Ollama with stream: false, reads response.data.message, and throws 'Ollama returned no message' if the shape is unexpected. The route converts that throw into HTTP 502.

Function:

    async function askConfiguredModel(messages, model) {

The model router:

    if (String(model).toLowerCase().includes('gemini')) return askModel1(messages, model);
    return askModel(messages, model);

Any model whose name contains "gemini" goes to the Gemini adapter; everything else goes to Ollama.

Function:

    function toGeminiSchema(schema) {

Gemini does not accept the additionalProperties field and handles schemas slightly differently. This recursive function strips unsupported fields (additionalProperties) from the tool parameter schemas while keeping properties and items, converting each nested schema the same way.

Function:

    async function askModel1(messages, model) {

The Gemini adapter. It:

1. Requires GEMINI_API_KEY and throws if it is missing.
2. Splits the conversation: the system message becomes systemInstruction; everything else becomes contents.
3. Converts message roles:
   - role "tool" becomes a user part with functionResponse (name + parsed JSON result).
   - role "assistant" with tool_calls becomes a model part with functionCall entries (name + parsed args), preserving thoughtSignature when present.
   - role "user" becomes a user part with text.
4. POSTs to:

    ${GEMINI_URL}/${model}:generateContent?key=${GEMINI_API_KEY}

   with systemInstruction, contents, and tools converted to Gemini's functionDeclarations format.
5. On HTTP errors, extracts Gemini's own error message when available and rethrows it.
6. Reads candidates[0].content.parts and throws 'Gemini returned no content' if missing.
7. Converts functionCall parts back into the Ollama-style shape:

    { function: { name, arguments: JSON.stringify(args), thoughtSignature? } }

8. Returns a normalized assistant message:

    { role: 'assistant', content: joinedText, tool_calls?: [...] }

This normalization is the key trick: the rest of the agent loop works identically for Ollama and Gemini because both adapters produce the same message shape.

Function:

    function parseArguments(rawArguments) {

Converts tool arguments into a JavaScript object. The model may send a real object or a JSON string; both are supported. Missing arguments become {}.

Function:

    function validateToolArguments(toolName, argumentsObject) {

A pre-execution guard for mutating tools:

- update_task_status: taskId must match /^TASK[0-9]+$/i and status must be one of todo, in_progress, blocked, done.
- assign_task: taskId must match /^TASK[0-9]+$/i and assigneeId must match /^EMP[0-9]+$/i.

If validation fails, the function returns an error object with guidance such as "Resolve the employee and list their tasks before updating each real task ID." The error is fed back to the model so it can recover by resolving real records first. This blocks a known failure mode where the model passes a tool name or a human name where an ID is required.

Function:

    async function runAgent(userMessage, options = {}) {

This is the main public function.

Validation:

    if (!userMessage || typeof userMessage !== 'string') throw new Error('message is required');

Model selection:

    const model = options.model || DEFAULT_MODEL;

Memory session and context:

    const memorySession = memory.createSession({ userId, conversationId, memoryPath });
    const relevantMemories = memory.search({ userId, query: userMessage, limit }, memorySession);
    const recentTurns = memory.getRecentTurns(memorySession);

The agent searches the user's long-term memories with the current message and reads the last few short-term turns. Both are packed into a second system message:

    const contextMessage = {
      role: 'system',
      content: JSON.stringify({
        shortTermConversation: recentTurns,
        relevantLongTermMemories: relevantMemories.memories,
        memoryPolicy: 'Use only relevant memories. Treat them as user-provided context, not as proof of current project data.'
      })
    };

The initial conversation is:

    const messages = [systemMessage, contextMessage, { role: 'user', content: userMessage }];

Request state:

    const log = [];
    const context = toolImpl.createContext({ persist: options.persist !== false, memorySession });
    const callCache = new Map();
    const failures = [];
    const mutatingTools = new Set(['update_task_status', 'assign_task']);
    const executionTrace = [];

- log: every executed tool call with arguments and result.
- context: an isolated copy of the project data plus plan/recommendation storage.
- callCache: deduplicates identical calls within this request.
- failures: collected errors for the final state.
- mutatingTools: the tools that require confirmation.
- executionTrace: iteration, tool, arguments, and outcome (completed/failed) for every attempt.

The loop:

    for (let iteration = 1; iteration <= MAX_ITERATIONS; iteration += 1) {

Model call with failure handling:

    try {
      assistantMessage = await askConfiguredModel(messages, model);
    } catch (error) {
      failures.push({ iteration, stage: 'model', error: error.message });
      return { finalAnswer: 'I could not continue because the local model failed. No risk conclusion was generated from incomplete evidence.', ..., stopped: 'model_error', ... };
    }

If the LLM itself fails, the agent stops honestly instead of inventing an answer.

Saving the assistant message:

    messages.push(assistantMessage);

Reading tool calls:

    const calls = assistantMessage.tool_calls || [];

This is the decision point: tool_calls means the model wants functions executed; no tool_calls means the model has produced its final text answer.

Final-answer branch:

    if (calls.length === 0) {
      memory.recordTurn({ userId, conversationId, userMessage, assistantMessage });
      return { finalAnswer, model, iterations, log, executionTrace, state: {...} };
    }

Before returning, the exchange is stored as a short-term conversation turn so follow-up questions in the same conversation have context.

Processing each call:

    for (const call of calls) {

Argument parsing with failure capture:

    try {
      argumentsObject = parseArguments(argumentsValue);
    } catch (error) {
      argumentsObject = {};
      argumentParsingError = error;
      failures.push({ iteration, tool: toolName, error: `Invalid tool arguments: ${error.message}` });
    }

Invalid JSON arguments become an error result instead of crashing the loop.

Cache key:

    const cacheKey = `${toolName}:${JSON.stringify(argumentsObject, Object.keys(argumentsObject).sort())}`;

The key is the tool name plus the arguments with sorted keys, so {a:1,b:2} and {b:2,a:1} count as the same call.

Argument validation:

    const argumentError = validateToolArguments(toolName, argumentsObject);

Malformed IDs or statuses for mutating tools are rejected before execution.

Confirmation gate:

    if (!result && mutatingTools.has(toolName) && !options.confirmed) {
      const confirmation = { confirmation_required: true, action: toolName, arguments: argumentsObject, message: '...' };
      log.push({ iteration, tool: toolName, arguments: argumentsObject, result: confirmation });
      return { ..., pendingConfirmation: confirmation, ... };
    }

The run stops with pendingConfirmation. Nothing is changed until the client resends the request with "confirmed": true.

Cache hit:

    if (!result && callCache.has(cacheKey)) {
      result = { cached: true, result: callCache.get(cacheKey) };
    }

Execution:

    if (!result) {
      try {
        if (!toolImpl[toolName]) throw new Error(`Unknown tool '${toolName}'`);
        result = await toolImpl[toolName](argumentsObject, context);
      } catch (error) {
        result = { error: error.message, retryable: true };
        failures.push({ iteration, tool: toolName, error: error.message });
      }
      callCache.set(cacheKey, result);
    }

The dynamic lookup toolImpl[toolName] is what allows the model to choose tools without the application containing an if statement for every possible question. Tool failures become normal JSON results so the model can replan.

Note that tools now receive a second argument, context. This gives them the request-scoped data copy, the memory session, and plan/recommendation storage.

Logging and trace:

    log.push({ iteration, tool: toolName, arguments: argumentsObject, result });
    executionTrace.push({ iteration, tool: toolName, arguments: argumentsObject, outcome: result && result.error ? 'failed' : 'completed', observed: result });

Sending the result back:

    messages.push({ role: 'tool', tool_name: toolName, content: JSON.stringify(result) });

This is the tool-calling handshake. The model reads the result and decides whether it has enough information or needs another tool.

Maximum-iteration result:

    return {
      finalAnswer: 'I could not complete the request within the tool-call limit.',
      model, iterations: MAX_ITERATIONS, stopped: 'max_iterations', log, executionTrace, state: {...}
    };

Export:

    module.exports = { runAgent, MAX_ITERATIONS };


6. src/tools.js - THE TOOL CATALOG
-----------------------------------

This file does not execute any data lookup. It defines descriptions of 17 functions for the LLM.

Every tool has this general shape:

    {
      type: 'function',
      function: {
        name: 'tool_name',
        description: 'When to use it',
        parameters: { type: 'object', properties: { ... } }
      }
    }

The description is part of the model's decision-making context. A vague description causes incorrect tool selection or arguments.

Planning tools:

1. create_plan - Create a dynamic plan for the current goal with ordered steps, dependencies, and the information each step must produce. Required: objective, steps. The system prompt tells the model to use this before a multi-project investigation.

2. replan - Revise the current plan after a tool failure, missing data, invalid data, or conflicting evidence. Required: reason, steps.

Read tools:

3. get_employee - Find an employee by exact ID or partial name, or list all employees with no filter. Returns ambiguous matches instead of guessing.

4. get_project - Find one project by exact ID or name. Use it to convert a human project name into a project ID before project-specific queries.

5. get_projects - List projects filtered by ownerId, ownerName, status, or name. The description prefers get_employee first, then ownerId; ownerName is a fallback that must resolve to exactly one employee.

6. get_tasks - List tasks filtered by projectId, assigneeId, assigneeName, status, pending=true, or overdue=true. pending means todo or in_progress; overdue means dueDate is before today and status is not done. The description explicitly forbids returning tasks for all employees when a person was named.

7. get_task - Get one task by exact ID. id is required.

8. calculate_project_metrics - Task counts and completion metrics for one project. Required: projectId. Use for progress summaries instead of fetching every task.

9. get_project_metrics - An alias that runs the same implementation as calculate_project_metrics. It exists so the model can use either name.

10. get_project_updates - List project updates, optionally filtered by projectId or riskLevel. The implementation also flags stale updates (older than 30 days) and conflicting updates (a project with mixed risk levels) as separate evidence.

11. find_project_risks - Analyze a project for delivery risks: overdue tasks, blocked tasks, inconsistent data (invalid status, missing due date, unknown assignee), assignee concentration, invalid deadlines, stale updates, conflicting updates, no task coverage, and schedule slippage. Each risk has a type and severity, plus an evidence block with the offending IDs.

Mutation tools (confirmation-gated):

12. update_task_status - Change a task status. Required: taskId, status. The description says it is impactful and requires user confirmation.

13. assign_task - Assign or reassign a task to an employee. Required: taskId, assigneeId.

Safe output tool:

14. create_recommendation - Create a structured recommendation (title, rationale, action, optional projectId and priority) from gathered evidence. It does not change task data, so it is safe to execute without confirmation.

Memory tools:

15. remember - Save durable user information only when the user explicitly asks. Required: key, content. A stable key lets a later statement update the same memory.

16. forget - Remove a stored memory by key when the user says it is no longer true.

17. search_memory - Retrieve relevant stored memories for the current request. The description forbids retrieving or mentioning unrelated memories.

Export:

    module.exports = { toolDefinitions };

Important distinction: the definitions in tools.js are only instructions and schemas. The actual behavior is in toolImpl.js.

Function: expandDefaultDataset

    expandDefaultDataset();

This runs only when the default data file is used (custom PM_DATA_PATH fixtures are never modified, which keeps failure scenarios easy to test). If the seed is smaller than 20 employees / 8 projects / 100 tasks / 20 updates, it expands the dataset in memory:

- Grows employees up to EMP24 (Team Member 5..24, alternating Engineering/Operations).
- Adds six projects: PROJ_DELTA, PROJ_EPSILON, PROJ_ZETA, PROJ_ETA, PROJ_THETA, and PROJ_EMPTY (a project with no tasks, used to test the no_task_coverage risk).
- Fills every project except PROJ_EMPTY up to 13 tasks, mixing todo/done/blocked statuses and deliberately overdue due dates.
- Appends one malformed task with assigneeId EMP999, dueDate null, and status "unknown" to test inconsistent-data detection.
- Builds a project_updates array with normal weekly updates, one old stale update for PROJ_ALPHA, one recent high-risk update for PROJ_ALPHA (deliberately conflicting risk levels), and filler medium-risk updates up to 24 total.

The result is a dataset with realistic problems: overdue work, blocked work, a taskless project, malformed records, stale updates, and conflicting risk levels. These give the risk-analysis tools real evidence to find.

      ...
    }

Writes mutations to disk atomically: first to a .tmp file, then rename over the real file. A crash mid-write cannot corrupt pm-data.json. The in-memory initialData is also refreshed so subsequent requests see the change. If writing fails, the caller rolls back the in-memory change and returns an error.

Function: getContextData

    function getContextData(context) {
      return context && context.data ? context.data : data;
    }

Every tool reads from the request context when one is provided, or from the shared data otherwise (direct tool usage in tests).

Helpers:

    function isTrue(value) { return value === true || value === 'true'; }

LLMs sometimes send the string "true" instead of a real boolean. This helper treats both the same for pending and overdue filters.

    function findById(items, id) { ... }

Case-insensitive ID lookup. EMP1 and emp1 both match.

    function normalizeStatus(status) { ... }

Standardizes status text: "In Progress" -> "in_progress", "in-progress" -> "in_progress", "TODO" -> "todo". Returns undefined for "pending" because pending is a group (todo + in_progress), not a stored status.

Function: get_employee

Same structure as before:

- No filters: return all employees with a count.
- Filter by exact ID (case-insensitive) or name substring.
- Zero matches: { error: 'No employee found', query }.
- Multiple matches: { ambiguous: true, message: 'Multiple employees matched; ask the user to clarify.', matches }. The tool never guesses which John the user meant.
- One match: return the employee.

Function: get_employee_by_query

    function get_employee_by_query(argumentsObject, context) {
      return get_employee(argumentsObject, context);
    }

An alias so either tool name works.

Function: get_project

Finds one project by ID (case-insensitive) or exact name (case-insensitive). Zero matches return an error; multiple matches return ambiguous; one match returns the project.

Function: get_projects

Lists projects with owner/status/name filters:

- ownerId is validated against the employee list. An invalid ID such as "get_employee" is rejected with guidance to resolve the name first. This prevents a false "Priya owns zero projects" answer when the real problem was a bad ID.
- A second defensive check re-verifies the normalized ownerId.
- ownerName is resolved by substring match: zero matches return an error, multiple matches return ambiguous, exactly one match converts the name to the employee ID.
- Projects are filtered by all supplied conditions and returned with a count.

Function: get_tasks

The most important filtering tool:

- projectId is validated; unknown projects return an error telling the model to call get_project first.
- assigneeId is validated the same way as ownerId.
- assigneeName resolves like ownerName, with ambiguity detection.
- A pending query without any project or assignee scope is rejected: "A pending task query needs an assigneeId, assigneeName, or projectId. Do not query all tasks for a person-specific question." This stops the model from dumping the entire task list.
- status "pending" (or pending=true) expands to todo OR in_progress.
- overdue compares dueDate to today's date and excludes done tasks.

Function: get_task

    function get_task({ id } = {}, context) {
      const task = findById(getContextData(context).tasks, id || '');
      if (!task) throw new Error(`Task '${id || ''}' was not found`);
      return task;
    }

Unlike the list tools, this one throws on a missing task. The agent loop catches the throw and converts it into { error, retryable: true }, which is exactly how the failure-recovery scenario is tested: the model sees the failure and switches to a scoped pending-task query.

Function: calculate_project_metrics

Computes totalTasks, doneTasks, inProgressTasks, todoTasks, overdueTasks, and completionRate for one project. Unknown projects return an error.

Function: get_project_metrics

    function get_project_metrics(argumentsObject, context) {
      return calculate_project_metrics(argumentsObject, context);
    }

An alias for the metrics tool under a second name.

Function: get_project_updates

Lists project updates with optional projectId and riskLevel filters, and adds two pieces of derived evidence:

- staleUpdateIds: updates older than 30 days (computed from today's date).
- conflictingUpdateIds: groups updates by project and flags any project whose updates contain more than one distinct riskLevel.

This is what lets the model notice contradictory status reports instead of silently picking one.

Function: create_plan

    function create_plan({ objective, steps } = {}, context) {
      if (!objective || !Array.isArray(steps) || steps.length === 0)
        return { error: 'A plan needs an objective and at least one step.' };
      context.plan = { version: context.plan ? context.plan.version + 1 : 1, objective, steps, status: 'active' };
      context.planHistory.push({ type: 'plan_created', plan: context.plan });
      return { planned: true, plan: context.plan };
    }

Stores the plan in the request context with a version number and records the creation in planHistory.

Function: replan

Same validation (reason + steps). It keeps the previous plan's objective, bumps the version, records the replanReason, and appends { type: 'replanned', reason, plan } to planHistory. The model is expected to call this when evidence conflicts or a tool fails.

Function: find_project_risks

The risk-analysis engine. For one project it inspects:

- overdueTasks (dueDate before today, not done) -> risk overdue_work, severity high.
- blockedTasks -> risk blocked_work, severity high.
- inconsistentTasks (status outside todo/in_progress/blocked/done, missing dueDate, or unknown assignee) -> risk inconsistent_data, severity medium.
- assignee concentration: if one assignee holds 3+ tasks -> risk assignee_concentration, severity medium.
- invalid deadline (missing, or deadline before startDate) -> risk invalid_deadline_data, severity medium.
- stale updates (from get_project_updates) -> risk stale_updates, severity medium.
- conflicting updates -> risk conflicting_updates, severity high.
- no tasks at all -> risk no_task_coverage, severity high.
- any not-done task past its due date -> risk schedule_slippage, severity high.

It returns the project, riskCount, the risks array, and an evidence object containing the exact task/update IDs behind every risk. The model is instructed to prioritize by severity and ground its recommendations in this evidence.

Function: update_task_status

    function update_task_status({ taskId, status, reason } = {}, context) {

Validates the task exists and the status is one of todo, in_progress, blocked, done. It saves the previous status, applies the change, and calls persistContext. If persistence fails, the change is rolled back and an error is returned. The success result includes updated, persisted, the task, previousStatus, and the reason.

Function: assign_task

Same pattern for reassignment: validates the task and the assignee, applies the change, persists atomically, rolls back on failure, and returns previousAssigneeId for auditability.

Function: create_recommendation

Builds a recommendation object:

    {
      id: 'REC_1',
      projectId: ... or null,
      title, rationale, action,
      priority: priority || 'medium'
    }

It is appended to context.recommendations and returned. It never touches task data, which is why it does not need confirmation.

Memory tool wrappers:

    function remember({...}, context) { ... }
    function forget({...}, context) { ... }
    function search_memory({...}, context) { ... }

Each checks that a memory session exists (returning 'Memory is unavailable without a user session.' otherwise) and delegates to src/memory.js with the session's userId.

Export:

    module.exports = {
      createContext,
      get_employee, get_project, get_projects, get_tasks, get_task,
      calculate_project_metrics, find_project_risks,
      update_task_status, assign_task, create_recommendation,
      get_employee_by_query, get_project_metrics, get_project_updates,
      create_plan, replan,
      remember, forget, search_memory,
    };


8. src/memory.js - LINE-BY-LINE EXPLANATION
--------------------------------------------

This module implements two kinds of memory:

- Long-term memory: durable facts the user explicitly asks to remember, stored in data/memory.json, isolated per user.
- Short-term memory: the last few conversation turns, held in a Node.js Map (in memory only, never promoted to long-term automatically).

Constants:

    const defaultMemoryPath = path.join(__dirname, '..', 'data', 'memory.json');
    const conversations = new Map();

The default storage file and the in-process conversation store.

Function: getMemoryPath

    return memoryPath || process.env.MEMORY_PATH || defaultMemoryPath;

The storage file can be overridden per call or with the MEMORY_PATH environment variable. Tests use a temp file so they never touch real user data.

Functions: emptyStore, readStore, writeStore

    function emptyStore() { return { users: {} }; }

    function readStore(memoryPath) {
      const filePath = getMemoryPath(memoryPath);
      if (!fs.existsSync(filePath)) return emptyStore();
      const parsed = JSON.parse(fs.readFileSync(filePath, 'utf8'));
      return parsed && parsed.users ? parsed : emptyStore();
    }

Reads the memory file, returning an empty store if the file does not exist or has an unexpected shape.

    function writeStore(store, memoryPath) { ... }

Writes atomically: creates the directory if needed, writes to a .tmp file, then renames over the real file. The same crash-safety trick used for pm-data.json.

Function: normalizeUserId

    return String(userId || 'anonymous').trim() || 'anonymous';

Every request belongs to a user; missing users become "anonymous". This is the basis of memory isolation.

Function: tokens

    function tokens(value) {
      return new Set(
        String(value || '').toLowerCase()
          .split(/[^a-z0-9_]+/)
          .filter((token) => token.length > 2),
      );
    }

A tiny tokenizer for relevance scoring: lowercase, split on non-alphanumeric characters, drop tokens of 2 characters or fewer (which removes noise like "is" and "to").

Function: userMemories

Gets (or creates) the memory array for one user inside the store. Users never see each other's arrays.

Function: remember

    function remember({ userId, key, content, type = 'preference', tags = [] } = {}, options = {}) {

- Requires key and content; otherwise returns an error.
- Normalizes the key to trimmed lowercase so "Priority" and "priority" are the same slot.
- If a memory with that key exists, it is updated in place (Object.assign) and the response says updated: true. Otherwise a new memory is created with an id like MEM_<timestamp>_<n>.
- Every memory stores key, content, type, tags, and updatedAt.
- The store is written to disk after every change.

This implements "update a stable key when it changes": saying "Project Beta is now my priority" replaces "Project Alpha is my priority" under the same key.

Function: forget

Finds the memory by normalized key and removes it with splice. Returns { removed: true, memory } or { removed: false, message: 'No matching memory found.' }.

Function: search

    function search({ userId, query, limit = 5 } = {}, options = {}) {

Keyword relevance search:

1. Tokenize the query.
2. For each of the user's memories, tokenize "key + content + tags" and count how many query tokens appear.
3. Keep only memories with relevance > 0 (unrelated memories are never returned).
4. Sort by relevance, then by most recently updated.
5. Return at most limit (default 5) with a count.

This is intentional lexical matching, not embeddings. It is deterministic, fast, and easy to test.

Function: conversationKey

    return `${normalizeUserId(userId)}::${conversationId || 'default'}`;

Short-term turns are keyed by user AND conversation, so alice's "planning" chat never leaks into bob's chat or alice's other chats.

Function: recordTurn

Appends { userMessage, assistantMessage, recordedAt } to the conversation's turn list and keeps only the last 8 turns (turns.slice(-8)). The bound prevents unbounded memory growth.

Function: getRecentTurns

Returns the last N turns (default 6) for a user/conversation. This is what the agent injects as shortTermConversation.

Function: createSession

    function createSession({ userId, conversationId, memoryPath } = {}) {
      return {
        userId: normalizeUserId(userId),
        conversationId: conversationId || 'default',
        memoryPath: getMemoryPath(memoryPath),
        relevant: [],
      };
    }

Creates the session object that agent.js and the memory tools pass around.

Function: clearMemoryCache

    function clearMemoryCache() { conversations.clear(); }

Clears all short-term conversation state. Tests use it between cases.

Export:

    module.exports = {
      remember, forget, search,
      recordTurn, getRecentTurns, createSession, clearMemoryCache,
    };

13. KEY DESIGN DECISIONS AND SAFETY FEATURES
---------------------------------------------

1. Evidence-driven looping, not a fixed workflow. The model decides the next tool from observed results. The system prompt forbids calling tools just to fill a sequence.

2. Honest stopping. Model failures produce stopped: 'model_error' with an explicit incomplete-evidence message. Reaching 15 iterations produces stopped: 'max_iterations'. The agent never fabricates a risk report from missing evidence.

3. Confirmation-gated mutations. update_task_status and assign_task always stop with pendingConfirmation until the client sends confirmed: true. The model cannot change data on its own authority.

4. Defense in depth against bad model output. validateToolArguments rejects malformed IDs before execution; toolImpl validates ownerId/assigneeId/projectId and rejects ambiguity instead of guessing; isTrue tolerates "true" strings; parseArguments tolerates object-or-string arguments.

5. Request isolation. Every run gets a deep-copied dataset via createContext, so concurrent requests and test cases cannot interfere. Persistence is an explicit opt-in behavior of the context.

6. Atomic writes. Both pm-data.json and memory.json are written to a .tmp file and renamed, so a crash cannot corrupt data. Failed persistence rolls back the in-memory change.

7. Duplicate-call caching. Identical calls within one request are served from callCache and marked cached: true, saving iterations and enforcing the "never repeat yourself" rule mechanically, not just by prompt.

8. Observability. Every response includes log (what ran), executionTrace (what ran and whether it completed or failed), and state (failures, plan, planHistory, recommendations, memoriesUsed, userId, conversationId). The agent's behavior is auditable, not hidden.

9. Memory discipline. Long-term memories are saved only on explicit user request, updated under stable keys, forgotten on request, searched by relevance only, and strictly isolated per user. Short-term turns are bounded (last 8 kept, last 6 injected) and never auto-promoted to long-term storage.

10. Dual-provider support through one normalized shape. Both the Ollama and Gemini adapters return the same assistant-message structure, so the agent loop, cache, validation, and confirmation logic are provider-independent.


14. MULTI-AGENT EXTENSION
--------------------------

The next version adds a small team of specialized agents coordinated by a Coordinator Agent. The goal is to understand collaboration between agents instead of asking one general-purpose agent to own every domain.

The specialists are:

    Project Agent
        Handles project identity, project status, delivery metrics, updates, and project-level risks.

    Task Agent
        Handles task lookup, overdue work, pending work, blocked work, and task-specific status questions.

    Employee/Workload Agent
        Handles employee lookup, project ownership, pending-task workload, and team capacity signals.

The implementation is in:

    src/multiAgent.js          Coordinator and specialist agent functions.
    src/routes/coordinator.js  HTTP endpoint for the coordinator.
    src/app.js                 Mounts POST /coordinator.
    test/multi-agent.test.js   Routing, collaboration, ambiguity, and shared-context tests.

The original POST /agent endpoint remains unchanged. It still demonstrates the LLM-driven tool-calling agent. POST /coordinator demonstrates deterministic multi-agent routing and collaboration over the same tool layer.


15. MULTI-AGENT ARCHITECTURE
-----------------------------

The flow is:

    Client query
        |
        v
    Coordinator Agent
        |-- classify intent
        |-- choose one or more specialists
        |-- create one request-scoped context
        |-- run specialists against that shared context
        |-- combine results into one response
        v
    Combined result or clarification request

The Coordinator does not duplicate project-management business logic. It delegates to existing toolImpl functions such as get_project, get_tasks, get_employee, get_project_metrics, find_project_risks, and get_projects. This preserves one source of truth for validation and data access. The LLM chooses the specialist; the specialist chooses the relevant existing tools.

The shared context is created with persist: false. That is intentional for this read-oriented coordinator: multiple specialists see the same snapshot, but a coordinator request cannot accidentally persist a mutation. The context also gives every specialist the same expanded dataset and the same request boundary.

The Coordinator now uses the configured LLM to understand natural language and choose agents. It sends a routing prompt that requires a JSON list of specialist names, validates that list against the known agent directory, and then invokes only the selected specialists. The chooseAgents keyword helper remains exported for compatibility and simple unit checks, but it is no longer the production routing path.

After specialist execution, the Coordinator sends the original query and structured specialist evidence to the LLM again. This synthesis step produces the human-readable finalAnswer. The raw results are still returned for transparency and debugging, but users no longer have to interpret the JSON themselves.

The Coordinator uses the same provider adapter as the original /agent endpoint. Its default model is qwen3:4b through Ollama. The request may select llama3.2 through Ollama or a Gemini model when GEMINI_API_KEY is configured. The coordinator route accepts an optional model field.


16. COORDINATOR ROUTING RULES
------------------------------

Project signals include project, portfolio, risk, metric, delivery, and update. These route to the Project Agent.

Task signals include task, overdue, late, pending, blocked, unfinished, incomplete, and assign. These route to the Task Agent.

Employee/workload signals include employee, person, people, team, workload, capacity, owner, and known employee names. These route to the Employee/Workload Agent.

Status is intentionally disambiguated:

    What is the status of Project Alpha?
        Project Agent only.

    What is the status of TASK1?
        Task Agent only.

    Tell me about the status.
        No specialist selected; the Coordinator asks for clarification.

When a query contains signals from several domains, the Coordinator selects several agents. For example, “Analyze Project Alpha overdue tasks and team workload” selects Project, Task, and Employee/Workload agents.


17. SPECIALIST RESPONSIBILITIES
-------------------------------

Project Agent:

1. Resolves a named project, or lists active projects when the query is portfolio-wide.
2. Collects metrics when the query asks about progress, completion, status, delivery, or risk.
3. Collects risk evidence when the query mentions risks, delays, blocked work, causes, or project health.
4. Collects update history when the query asks for updates, latest reports, stale updates, or conflicting updates.

Task Agent:

1. Resolves a project name before querying project-specific tasks.
2. Applies overdue and pending filters based on the query.
3. Resolves a named employee when a task query is person-specific.
4. Returns the actual task records and count, rather than inventing a summary.

Employee/Workload Agent:

1. Resolves a named employee, or lists employees for a general team query.
2. Finds projects owned by each employee.
3. Finds pending tasks assigned to each employee.
4. Returns ownership and workload evidence that can be combined with project and task results.

20. WHY MULTIPLE AGENTS ARE USEFUL
-----------------------------------

Specialization reduces the amount of domain knowledge each agent needs to reason about. The Project Agent does not need to understand employee workload rules, and the Employee/Workload Agent does not need to own project risk analysis.

Specialization also improves observability. The system can show which agent produced which evidence, making it easier to identify whether a bad answer came from routing, project analysis, task filtering, or workload calculation.

The trade-off is coordination overhead. More agents mean more interfaces, more routing decisions, and more opportunities for inconsistent results. The shared request context and structured results reduce this risk, while tests make the routing contract explicit.


21. LIMITATIONS AND NEXT STEPS FOR THE MULTI-AGENT DESIGN
-----------------------------------------------------------

1. LLM routing can still misunderstand synonyms or complex language. The JSON routing contract and agent-name validation reduce, but do not eliminate, that risk.

2. The current Coordinator uses one LLM synthesis call after specialist execution. A future dedicated synthesis stage could compare contradictions and produce a more analytical final report.

3. Specialists currently run sequentially in JavaScript. Independent specialists could run concurrently with Promise.all while retaining one immutable read snapshot.

4. The coordinator endpoint is read-only by design. Future mutation workflows should route proposed changes through the existing confirmation gate and return one combined approval request.

5. The project still uses JSON data and file-backed memory. Production multi-agent deployments would need a database, authentication, audit logs, tracing, timeouts, and per-agent access policies.

The main learning is that collaboration is an architecture: a coordinator decides who should act, specialists own bounded responsibilities, shared context keeps their evidence consistent, and structured results make synthesis and debugging possible.
