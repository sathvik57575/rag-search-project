MULTI AGENT COORDINATOR ROUTE (/coordinator) TECHNICAL DOCUMENTATION


1. OVERVIEW & ARCHITECTURE

I built the /coordinator route so that complex project management requests can be handled by multiple specialized agents working together. The old /agent route runs one single agent with all 18 tools, but I found that for big questions, having one coordinator agent supervise smaller specialist agents works much better.

System Architecture Diagram:

2. NEW FILES AND WHAT I BUILT IN EACH

A. src/app.js (Route Registration)
I updated src/app.js to import coordinatorRouter and mounted it at /coordinator:
const coordinatorRouter = require('./routes/coordinator');
app.use('/coordinator', coordinatorRouter);

B. src/routes/coordinator.js (HTTP Endpoint)
I created this file to handle POST requests to /coordinator. It checks that the user sent a valid query string in req.body, calls runCoordinator(query, { model }) from multiAgent.js, and sends back the JSON result.

C. src/multiAgent.js (Core Coordinator & Specialist Logic)
I built this file as the main engine for multi-agent delegation. Here is what I put in it:

1. SPECIALIZED_AGENTS Directory:
I defined three specialist agents:
- project: Handles project status, metrics, updates, and risks.
- task: Handles task searches, overdue work, pending tasks, and task status.
- employee: Handles employee lookups, project ownership, and workload.

2. isGenericAmbiguousQuery(query):
I added this function to catch vague prompts like "Tell me about the status.." that do not mention any specific project, employee, or task ID. When it catches one, I stop early and ask the user for clarification.

3. runCoordinator(query, options):
This is the main function I wrote to run the multi-agent workflow:
- First I run the ambiguity check.
- If it passes, I ask the model to pick which agents we need ("project", "task", "employee"). I turn off tools (useTools: false) and set format: "json" so local models like Llama3.2 do not get confused.
- If model routing fails or gives bad JSON, I use my fallback function chooseAgents(query) so it never crashes.
- Next I create one shared execution context (tools.createContext({ persist: false })) and run the chosen specialist runners.
- Finally I ask the model to synthesize all specialist evidence into one clear answer. If synthesis fails, I use my summarize() helper function as a fallback.

4. Specialist Runners:
- runProjectAgent: Looks up projects using get_project / get_projects and attaches metrics, risks, and updates.
- runTaskAgent: Finds matching tasks using get_tasks with overdue or pending filters.
- runEmployeeAgent: Looks up employee details, owned projects, and workload using get_employee and get_tasks.


3. STEP-BY-STEP HOW A REQUEST WORKS

Step 1: The user sends a POST request to /coordinator with a query and model name.
Step 2: I check if the query is too ambiguous. If it is vague without a specific target, I stop and return status "needs_clarification".
Step 3: If it has a target, I ask the model to pick the agents. If model routing fails, my chooseAgents() fallback picks them.
Step 4: I create one shared context object so all agents inspect the exact same data.
Step 5: The selected specialist runners fetch project, task, or employee data from toolImpl.js.
Step 6: I pass the query and all specialist results to the synthesizer prompt to write the answer. If that fails, summarize() writes it.
Step 7: The server returns the final JSON response to the user.


4. MODEL PERFORMANCEs
Gemini (gemini-3.5-flash-lite): Works great for both routing and synthesis

qwen3:4b: Works well for most cases.

Llama 3.2: Failed some multi-agent routing cases because Ollama was sending tools in the API body. I fixed this by setting useTools: false for routing calls and adding fallback functions so Llama queries always complete successfully.

Analysis of report and KEY areas of improvement

I added a total of 21 requests, and most of them returned correct answers, some of them resulted in failure due to various reasons.

Detailed error analysis:

Request 6: ratio of todo, in_progress, done tasks (llama3.2)

The query asked for a ratio across 105 tasks. The finalAnswer just said "Task Agent found 105 matching task(s)" and stopped there, no numbers at all. This happened because the model was handed a huge JSON array as context and instead of iterating through every entry and tallying status counts, it just given up on the counting step entirely and just described the result set size. Small local models like llama3.2 have weak instruction following once the input gets long, so they tend to summarize what they see rather than execute a multi step procedure like "count how many have status X then status Y, then status Z, then express as a ratio." 


Request 16: ratio of estimated hours across todo, done, in_progress (llama3.2)

Here the model did attempt to do the work, but it invented an "hours per task" average(10.4 hours/task) that isn't there in the data, then multiplied that average by task counts to get totals. This is a hallucinated result. Rather than summing actual estimated hours values across every task object (which is tedious and requires tracking a running total across 50 plus entries), it approximated with a made up average and presented the result with full confidence, including decimal precision that implies real calculation. This is a known weakness of smaller models on long numeric extraction tasks, they substitute a plausible sounding values when the actual computation exceeds their working memory or token limit/context span over long context.


Request 14: total estimated hours of todo tasks (qwen3:4b)

This took 25 minutes and returned 511 instead of the correct 603. There are two separate problems here. First is latency, qwen3:4b is a larger, slower model for my laptop, so processing the full payload took an large amount of time regardless of accuracy. Second is that despite extra time, it still got the math wrong and gave zero explanation, just returned final number with no work. That suggests it wasn't actually summing every relevant entry either, it likely lost track partway through the array or some subset of tasks, similar to llama3.2 but was even slower than llama3.2 when it comes to this.


Request 19: ratio of projects to tasks due by month end(llama3.2)

The correct answer which was confirmed by gemini in Request 20 on the same data, is 5 projects to 71 tasks. But llama3.2 said 3 projects and 20 tasks. This suggests thelogic itself was applied inconsistently, it likely compared deadlines against this month literally rather than correctly interpreting the requested window, or dropped some projects whose deadlines were on boundary dates. So this is another model limitation where llama3.2 is just not smart enough.

Areas of improvement:

1. Parallel Specialist Agent Execution
Currently in my project i.e src/multiAgent.js, specialist functions run synchronously in sequence using .map().
Improvement: If specialist agents need to fetch data asynchronously, update execution to use Promise.all() to run specialists in parallel, reducing overall response latency, this would be a lot better in both time and accuracy.


2. Adding Conversation Memory to the Coordinator Route
The /coordinator route is currently completely stateless. Unlike the /agent route (which manages short term sliding window history and long-term memory in data/memory.json), the /coordinator route treats each incoming request independently without reading or recording conversation history.
Improvement: We can integrate session memory and conversation tracking (keyed by conversationId and userId) just lije we did in /agent route. This would allow multi requests to retain context. Context is very impotant in a multi agent system.

3. Native Structured Outputs (JSON Schema Mode)
Currently we are routing response parsing uses regex string matching (parseJsonResponse).
Improvement: Instead we can use native structured Outputs or JSON Schema mode supported by Ollama (format: schema) and Gemini (responseSchema). This guarantees 100% strict JSON schema output from models without relying on string regex parsing.

4. Semantic Memory Search with Vector Embeddings
Currently there is no smart memory search in src/memory.js.
Improvement: We can integrate a lightweight local vector embedding model so queries like "wHat are my work priorities?" retrieve memories like "Project I want to focus on is project delta" even when there is no direct keyword overlap.


5. Payload oversizing.
When I was testing random queries, I noticed, for some queries, the payload size exceeds the local models' context length even though it only happens sometimes, and not always. Due to this, the models return failed responses.
There is a fallback which I implemented. This is a summarize() function which just summarizes the results and gives a generic answer instead of relying on the LLM.
Improvement: When we get a 400 or 429 error from the LLM, we can trim large raw task arrays and, example when the task counts exceed 50, we can just send the count and first 15 tasks instead of all tasks. It will calculate the approzimate value and give us the result.
So let's say there are too many tasks objects, what we actually do is 
When total tasks exceed 50, we:
Pre calculate the total counts per status(statusCounts).
Remove the 105 item tasks array.
Replace it with a 15 lightweight item sampleTasks array containing only key metadata (id, projectId, title, status, assigneeId).
We can even randomly choose what tasks to send.
This way we don't hit the limit.
I ACTUALLY IMPLEMENTED IT THIS WAY, BUT LATER REMOVED IT AS THE MODELS STOPEPD THROWING ERRORS for LARGE PAYLOADS FOR SOME REASONS, AND GAVE ME CORRECT ANSWERS INSTEAD OF USING summarize.
